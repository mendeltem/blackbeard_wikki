Aussage

Ein gültiges Schema, eine schöne Beschreibung oder hohe Wortüberlappung zwischen Aufgabe und Werkzeugtext beweisen nicht, dass ein Agent das Werkzeug findet und richtig aufruft. rea verlangt dafür Läufe mit repräsentativen Aufgaben, breit und direkt formuliert, auf dem Host und Modell, für die das Werkzeug gedacht ist. Festgehalten wird je Lauf:

  • Host und Modell
  • der Werkzeugkatalog, den das Modell tatsächlich sah
  • gewähltes Werkzeug und Argumente
  • Fehler und Wiederholungen
  • ob die Aufgabe gelöst wurde

Auch die Größe des Katalogs in Bytes misst weder Nutzbarkeit noch Kontextkosten für das Modell.

Trägt

Jede Änderung an Werkzeugnamen, -beschreibungen oder Toolsets für Hermes, OpenCode oder eigene MCP-Server. Zwei eigene Fälle passen dazu: - Das Nous-Repo hermes-agent-self-evolution bewertet Skill-Varianten mit einer Wortüberlappungs-Metrik, siehe self-evolution-gepa-silently-falls-back. Nach dieser Regel misst das nichts über die Werkzeugwahl. - Laya als Werkzeug innerhalb von Hermes brachte keinen Zeitgewinn, Laya als Weiche davor 0,1 s je Entscheidung, siehe laya-router-before-agent. Das zeigte erst der echte Lauf, nicht die Konfiguration.

Trägt nicht

Wie viele Läufe reichen. rea nennt keine Zahl.

Bruchindikator

Eine Werkzeugänderung wird als Verbesserung gemeldet, ohne dass eine Spur mit gewähltem Werkzeug und Ergebnis vorliegt.
