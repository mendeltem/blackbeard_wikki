Mehrere Agenten und Chats arbeiten gleichzeitig an denselben Repos, ohne voneinander zu wissen. Hier steht, was dabei schiefgeht und was dagegen hilft.

Der rote Faden: der Schaden entsteht nicht beim Schreiben, sondern beim Annehmen. Ein überschriebener Stand, ein fremder Commit, eine stumm falsch gelesene Datei — in allen drei Fällen hat niemand einen Fehler gemacht, der sichtbar geworden wäre.

RegelMain rule: all work is in Englishgetragen2026-10-15

Herkunft: Mendel, chat on workstation Alita, 2026-10-15 ("ein Hauptregel in wiki sollte alle Arbeiten sollten auf Englisch sein") · eigene Seite · Markdown

Statement

Everything an agent produces is written in English: wiki entries (title, body, section headings), code, comments, commit messages, file and folder names, QC pages, tables and their column/sheet names, reports, primers and figures. The chat with Mendel may stay in German; the artefacts do not. Existing German entries are translated when they are next touched (no big-bang rewrite); a new entry is never written in German. Exception: the frontmatter keys and their fixed values (typ: regel, status: getragen, stand, herkunft, ...) stay as defined in templates/knowledge-entry.md, because wiki_maintenance --check validates them.

Applies to

All agents and chats that write to this wiki or produce files for Mendel's projects.

Does not apply to

Quotes of what a person said (keep the original wording, add an English gloss if needed); data that arrives in another language (e.g. German DICOM series names) is kept as it is.

Break indicator

A new entry, page or table in German, or a translated entry whose numbers no longer match the original.

Source

Mendel's instruction 2026-10-15; earlier the same rule for outputs (QC pages, Excel, GitHub) since 2026-09-29/10-12.

RegelMenschen lesen HTML, Agenten schreiben Markdown: die Wiki hat eine Quelle und eine erzeugte Lesefassunggetragen2026-10-11

Herkunft: Nutzerregel Mendel 2026-10-11 (Wiki und Tafel), Bau von tools/general/wiki_html · eigene Seite · Markdown

Aussage

Alle Information der Wiki wird für Menschen über die erzeugte HTML-Seite gelesen (docs/index.html, mit Links auf jede andere Seite, Suche, Kurzstand je Bereich, Einträge aufklappbar, Verweise und Rückverweise, Plots). Die Quelle bleibt Markdown mit Frontmatter, eine Datei je Aussage, wie im README beschrieben; nur die README.md ist zugleich Quelle und Lesetext. Agenten schreiben nie HTML von Hand in die Wiki. Nach jedem Beitrag wird docs/ mit tools/general/wiki_html neu gebaut und mit eingecheckt (lokal übernimmt das der pre-commit-Haken). docs/ wird nie von Hand bearbeitet; was dort fehlt, fehlt in der Quelle.

Trägt

Gilt für diese Wiki und sinngemäß für die Tafel (BLACKBOARD.md als Funktionskern, Tafel-HTML als Lesefassung). Gründe für Markdown als Quelle: dieselbe Information kostet in HTML etwa das Zwei- bis Dreifache an Tokens, und SUMMARY.md geht als Prefill in lokale Modelle mit knappem Kontext; kleine lokale Modelle schreiben Markdown zuverlässig und lassen in HTML Tags offen; Markdown-Diffs lassen sich bei parallelen Sitzungen lesen und zusammenführen; Prüfwerkzeug, Vorlagen, Skill und claude.ai-Projekt hängen am Frontmatter. Maschinen bekommen zusätzlich docs/index.json (Titel, Pfad, Bereich, Typ, Status, Stand, Kurztext je Eintrag).

Trägt nicht

Eine Veröffentlichung über GitHub Pages: für das private Repo im aktuellen Plan nicht möglich (geprüft 2026-10-11, HTTP 422). Bis dahin wird docs/ aus dem Clone gelesen oder über einen lokalen Server. Ein öffentliches Pages-Repo würde den Wiki-Inhalt öffentlich machen und ist eine eigene Entscheidung von Mendel.

Bruchindikator

Ein Eintrag steht nur in docs/ und nicht in knowledge/; eine Sitzung schreibt HTML-Dateien von Hand; docs/index.html ist älter als der jüngste Markdown-Commit (dann fehlt der Haken in diesem Clone, siehe tools/general/wiki_html/INSTALL.md).

Ablesung

Nutzeranweisung 2026-10-11 ("statt md außer dem ersten README.md sollte alle Information jetzt nur über HTML gehen; index.html mit Links zu jedem anderen HTML, intelligent gebaut"), Entscheidung im Gespräch: Markdown bleibt Quelle, HTML wird erzeugt. Tier: Setzung des Nutzers plus Messung (Linkprüfung 5463/0 tot).

Verknüpft

one-filename-two-contracts: Quelle und Lesefassung sind zwei Dateien mit je einem Zweck. wiki_html, wiki_maintenance.

RegelVerknüpfte Seiten: eine Zuordnungsdatei, feste Adressen, Rückweg im Generatorgetragen2026-10-06

Herkunft: Claude-Code-Sitzung, Verknüpfung ai_use_cases_overview / Supply_Atlas3D / AI_Companys, 2026-10-06 · eigene Seite · Markdown

Aussage

Vier Seiten sind seit 2026-10-06 gegenseitig verlinkt: ai_use_cases_overview (Use-Case-Karten), Supply_Atlas3D (Globus mit Standorten), AI_Companys (Firmenkennzahlen) und diese Wiki (Hintergrund: Mechanismen, Befunde). Die Startseite mendeltem.github.io führt alle vier unter „Meine Projekte“. Damit das so bleibt, gelten vier Regeln.

  1. Eine Zuordnungsdatei. Alle Verknüpfungen stehen in ai_use_cases_overview/deployments.json, nirgends sonst. Abschnitte: - use_cases.<slug>.places: Orte je Use Case; entweder {"site": "<Name im Atlas>"} oder eigene la/lo mit Satz und Quelle. - companies.names, companies.operators (Textstücke, gegen das Betreiberfeld ow im Atlas gesucht), companies.use_cases (Karten-Slug → Ticker, nur wenn die Karte die Firma selbst nennt), companies.cards (Kartennamen DE/EN), companies.relations (Rollen jenseits des Betreibens: fertigt, liefert HBM, montiert, nutzt GPUs; geht im Atlas vor dem Textabgleich). - wiki: entries (Pfad → Titel DE/EN), use_cases (Slug → Pfade), companies (Ticker → Pfade), atlas.ai_use (bei jedem KI-Beleg im Atlas), atlas.layers (Atlas-Schicht → Pfade). Pfade relativ zu knowledge/. Alle drei Seiten lesen sie zur Laufzeit per fetch. Gleiche Domain, GitHub Pages liefert Access-Control-Allow-Origin: *.
  2. Feste Adressen, nicht ändern ohne alle drei Seiten: - Karte: ai_use_cases_overview/#uc=<slug>, Slug = englischer Kartenname klein, Nicht-Alphanumerisches → -. - Globus je Use Case: Supply_Atlas3D/?uc=<slug>; je Firma: ?company=<TICKER>; Test mit eigener Datei: &dep=<datei>. - Firma: AI_Companys/nvidia-oekosystem.html#/<de|en|mn>/<TICKER>. - Wiki: github.com/mendeltem/blackbeard_wikki/blob/main/knowledge/<pfad>. Einen Eintrag umbenennen heißt: Pfad in deployments.json mitziehen. Im Atlas sind Use Cases und Firmen zusätzlich über das Menüfeld „Use Cases & Firmen“ wählbar; die Adresse wird dabei mitgeschrieben.
  3. Rückweg auf generierten Seiten gehört in den Generator. AI_Companys wird täglich von einer Pipeline neu geschrieben; werkzeuge/seite.py trägt Ergänzungen danach über Marker wieder auf. Der Verbundblock steht dort als eigener Schritt (/* verbund-hilfe */, Stil verbund, Texte vb_*), die Schwesterlinks auf der Übersicht ebenso (<!-- schwester -->, Stil schwester). Direkt in die HTML geschrieben wäre er am nächsten Morgen weg.
  4. Vor jedem Push prüfen: python3 werkzeuge/verbund_pruefen.py im Repo ai_use_cases_overview prüft Slugs, Atlas-Standorte, Ticker, Kartennamen und Wiki-Pfade gegen die veröffentlichten Seiten (oder lokale Klone mit --atlas, --firmen, --wiki). Ausgang 1 bei Fehler.

Trägt

  • Einen neuen Ort oder eine neue Firmen-Zuordnung eintragen heißt: eine Zeile in deployments.json. Keine Seite muss neu gebaut werden.
  • Fällt der Abruf aus, verschwinden die Verbundteile still; die Seiten bleiben benutzbar.

Trägt nicht

  • Einen Kartennamen ändern, ohne den Slug in deployments.json mitzuziehen: Links laufen dann ins Leere, ohne Fehlermeldung.
  • Einen Atlas-Standort umbenennen: {"site": ...}-Verweise finden ihn nicht mehr und fallen weg.
  • Den Rückweg auf AI_Companys von Hand in die HTML schreiben.

Bruchindikator

Ein Link landet auf einer Karte, die nicht aufklappt, oder ein Use Case zeigt im Atlas weniger Orte als in deployments.json stehen. Prüfen: werkzeuge/verbund_pruefen.py (findet beides), im Atlas ucPlaces(UC_ALL[slug]).length gegen places.length.

RegelEin Dateiname, ein Zweckgetragen2026-10-02

Herkunft: Projekt Verbund, Datenvertrag 2026-09-05 bis 2026-09-16 · eigene Seite · Markdown

Aussage

Sobald mehrere Projekte Daten austauschen, entsteht ein naheliegender Name — daten.json — und zwei Ansprüche darauf: die Datenquelle, aus der eine Seite sich selbst speist, und die Außenschnittstelle, über die andere sie lesen. Solange ein Projekt allein steht, fällt das nicht auf. Sobald mehrere Agenten dieselben Repos bauen, besetzt jeder den Namen für seinen Zweck.

Der Fall: zehn Seiten in neun Repos sollten je eine vertragskonforme daten.json liefern. In drei Repos war daten.json zuerst die Datenquelle der Seite; der Vertrag landete daneben in daten-verbund.json. Die lesende Seite zeigte auf daten.json, fand dort eine gültige JSON-Datei ohne das Feld indikatoren — und meldete nichts. Kein Fehler, kein Abbruch, nur drei Quellen mit null Indikatoren, die aussahen wie Quellen, die eben noch nichts zu sagen haben.

Drei Maßnahmen, zusammen:

  1. Eigener Name für die Schnittstelle. Wer exportiert, exportiert unter einem Namen, den sonst niemand will.
  2. Namensraum prüfen, nicht nur Form. Die Datei nennt, für wen sie spricht (seite: "energie"), und jeder Schlüssel trägt dieses Präfix (energie.energisierte_gw). Der Leser prüft beides gegen das, was er erwartet hat.
  3. Verweigern statt übernehmen. Eine Datei, die den Vertrag verletzt, wird nicht eingelesen, sondern mit Grund gemeldet.

Punkt 3 ist der entscheidende: ohne ihn ist eine falsch benannte Datei von einer leeren nicht zu unterscheiden — siehe empty-is-not-missing.

Trägt

Jeden Datenaustausch zwischen Repos, die von verschiedenen Sitzungen gebaut werden. Auch Konfigurations- und Zwischenstandsdateien: config.json, state.json, index.json haben dasselbe Problem.

Trägt nicht

Ein Projekt, das für sich steht. Dort ist daten.json der richtige Name, und eine Umbenennung auf Vorrat ist Aufwand ohne Ertrag.

Auch keine Aussage über das Format. Der Vertrag kann beliebig aussehen; es geht darum, dass er einen eigenen Namen hat und beim Lesen geprüft wird.

Bruchindikator

Ein Leser, der bei der falschen Datei still weitermacht. Prüfprobe: dem Leser eine bewusst falsche Datei vorlegen — sagt er nichts, prüft er nicht.

Zweiter Indikator: eine Quelle, die über Wochen null Einträge liefert, ohne dass jemand sagen kann, ob sie leer ist oder falsch gelesen wird.

Ablesung

Eigene Messung, Projekt AI_Lage. Am 2026-09-16 waren 3 von 10 Quellen betroffen; das Leswerkzeug mit Vertragsprüfung meldete sie namentlich, danach 10 von 10 konform, 24 Indikatoren statt 3. Keine fremde Quelle.

RegelNicht in einen fremden Arbeitsbaum schreibengetragen2026-10-02

Herkunft: Projekt Verbund 2026-09-05 und blackbeard_wikki 2026-10-02 · eigene Seite · Markdown

Aussage

An denselben Repos arbeiten mehrere Sitzungen gleichzeitig. Keine von ihnen sieht die andere. Daraus folgen drei Regeln, alle aus Schaden gelernt:

Vor dem Schreiben Zeitstempel lesen.

ls -la --time-style=+%H:%M:%S

Bewegen sich Dateien im Minutentakt, läuft dort eine andere Sitzung. Bei einem Git-Repo ist .git der empfindlichste Zeiger: jünger als ein paar Minuten heißt aktiv.

Nicht in den fremden Arbeitsbaum schreiben, sondern in einen eigenen Klon. Der Grund ist nicht der Schreibkonflikt — die eigenen Dateien liegen meist auf neuen Pfaden und kollidieren gar nicht. Der Grund ist das git add -A der anderen Sitzung: es nimmt die fremden Dateien mit in ihren Commit und pusht sie, ohne dass irgendjemand sie freigegeben hätte. Aus einem Lesevorgang wird so eine Veröffentlichung.

Den eigenen Lesestand als veraltet behandeln. In einem aktiv bearbeiteten Repo ist jede Übersicht, die älter als Minuten ist, falsch.

Trägt

Jedes Repo, in dem mehr als ein Agent oder Chat arbeitet, und jedes gemeinsame Gedächtnis. Auch diese Wiki: sie ist der Fall, für den die Regel zuletzt gebraucht wurde.

Der eigene Klon ist billig. Ein ungewollt gepushter Commit ist es nicht.

Trägt nicht

Sperren oder Reservierungen. Es geht um Lesen vor dem Schreiben und um Trennung der Arbeitsbäume, nicht um ein Protokoll, an das sich alle halten müssten — denn genau das lässt sich zwischen Sitzungen nicht durchsetzen.

Auch kein Argument gegen das gemeinsame Repo. Die Alternative — jeder sein eigenes — ist teurer.

Bruchindikator

Ein Commit, der Dateien enthält, die niemand in dieser Sitzung geschrieben hat. Oder: zwei Einträge zum selben Gegenstand, die voneinander nichts wissen.

Ablesung

Zwei eigene Fälle, beide beobachtet, keine fremde Quelle.

2026-09-05, Verbund: eine parallele Sitzung baute drei Seiten und schrieb in jedem Repo eine eigene daten.json — dabei wurde eine vertragskonforme Datei zweimal überschrieben. Folge siehe one-filename-two-contracts.

2026-10-02, blackbeard_wikki: eine Prüfung auf einen lokalen Klon ergab "nicht vorhanden"; wenige Minuten später existierte er, .git war 60 Sekunden alt, der Klon lag 6 Commits hinter origin/main und hatte 2 ungepushte Commits. Zwischen zwei Lesungen im Abstand von rund zwei Stunden wuchs die Wiki von 2 auf 15 Themen. Der Abgleich der ersten Lesung war zum Zeitpunkt des Schreibens vollständig veraltet.
