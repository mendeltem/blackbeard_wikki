Mehrere Sitzungen in denselben Repos: fremde Arbeitsbaeume, doppelt belegte Dateinamen

Agenten, parallele Sitzungen, Repos, Branches, Datenaustausch, Seitenverbund, deployments.json, Verlinkung

9 getragen 2 vorschlag

Mehrere Agenten und Chats arbeiten gleichzeitig an denselben Repos, ohne voneinander zu wissen. Hier steht, was dabei schiefgeht und was dagegen hilft.

Abgrenzung zu agent_tooling: dort geht es um ein Werkzeug und seine Ausgabe, hier um zwei Sitzungen und ein gemeinsames Repo.

Der rote Faden: der Schaden entsteht nicht beim Schreiben, sondern beim Annehmen. Ein überschriebener Stand, ein fremder Commit, eine stumm falsch gelesene Datei — in allen drei Fällen hat niemand einen Fehler gemacht, der sichtbar geworden wäre.

RegelDo not log case-level contentvorschlag2026-10-21

Herkunft: user instruction 2026-10-21 ("wichtig logs da nicht machen"), own runs 2026-10-21 · eigene Seite · Markdown

Aussage

A log is a copy. Write no case-level content into logs, caches or agent session stores - not for class 3, not for class 2, and not into a temporary directory that sits next to the data. Case-level means anything that identifies or reconstructs an individual record: subject or session ids, file paths, image headers, individual values, names, image files, unredacted report text.

Rule of thumb: if it must not be committed, it must not be logged either. The same content that is too sensitive for a repository is too sensitive for a text file that happens to be called a log. A log is usually easier to find and harder to forget than the data itself.

What is allowed and wanted: counts, durations, exit codes, decision outcomes, error classes, aggregate numbers, file names of code (not of data). "23 files processed, 4 skipped, exit 0" is a good log line. "sub-XXXX ses-YY image malformed" is not.

Trägt

It settles a whole class of small decisions without a judgement call each time: no debug output on by default, no "Vorgang gespeichert" file, no keeping last night's output "in case it is useful", no session store collecting the ids that were inside a prompt. The place for the run's own intermediate state is a temporary directory owned by that run, deleted when it ends - not a persistent history.

It also protects against the case that is easy to miss: the log of a program we did not write. An agent harness, a service, a scheduler or a database keeps its own history. With Hermes, conversations land in the profile's state database by design. That is one more reason not to put the content in the prompt or the tool output in the first place - what never arrives cannot be stored.

Standing check, own runs 2026-10-21: /tmp held exactly this kind of leftover from the day's work (image test logs, a background-visibility probe file, dispatcher output). None of it contained patient data because the work happened on the Cle side, but a probe file in a working directory is precisely the habit this rule forbids.

Trägt nicht

It does not forbid logging the decision. An audit trail is wanted and, for class 2 and 3, often required: which dataset, which class, which rule, what was decided, and when - about the data, never from the data. The guard log is not a violation, it is the point, as long as it records the decision and not the content (no excerpt field, no "logged value").

It also does not forbid a short-lived in-memory trace while debugging one run, if that run is local and the trace dies with the process. What it forbids is the persistence: the file that outlives the run, the cache that is still there next week, the shared directory that someone else can read.

Bruchindikator

A log, cache or session store contains subject ids, session ids, data or image paths, individual values, image headers or unredacted report text. A debug output file or probe file is left in a working directory. Intermediate state is put next to the data instead of in the run's own temporary space. A log line is defended with "it is only the file name" - file names are case-level content. A tool is used with its default history on a class-2 or class-3 job.

Ablesung

Decided in the same session as the class rule, so it is written next to it: three-data-classes-decide-what-may-leave-the-institution. Content that may not leave the institution at all: remote-model-gets-only-data-free-skills-and-redacted-text. Existing finding that an agent harness keeps its own history: hermes-keeps-every-conversation-in-state-db.

RegelThree data classes decide what may leave the institutionvorschlag2026-10-21

Herkunft: user decision 2026-10-21 ("drei verschiedene klassen": fully open / institution-usable / completely private) · eigene Seite · Markdown

Aussage

Every dataset gets exactly one class before any agent touches it. The class decides the route, not the tool and not the question. This is a main rule: it applies to every area of this wiki, not to one project.

  1. Class 1 - fully open. No registration, no data use agreement; open challenge data (e.g. VALDO, the WMH challenge of the MICCAI line). May go anywhere open data may go: public GitHub, any cloud, any remote model, any agent. The limit is the licence, not the route - if a platform forbids redistribution, the platform copy stays out even though the data is open.
  2. Class 2 - institution-usable, access-restricted. Access was granted to the institution under a data use agreement or registration, and that grant is what permits processing. Example: HCP-Aging (AABC). Its terms allow a local copy "for non-commercial research use" and allow sharing within my institution (e.g. on a shared server) under the same terms, with every individual user bound. So the institutional hub (Cle, Charite-internal) may process class 2. Not permitted: GitHub, public cloud, external APIs, redistribution outside the institution.
  3. Class 3 - completely private. Own patient cohorts. The data stays local: no case on GitHub, no case in any cloud, institutional one included. Local profile and local model only.

The class belongs to the data, not to the task. This is the decisive point: a class-3 job is not automatically a local job. Thinking, reasoning, planning and coding about class-3 work contain no patient data as long as no case id, image, path or report sentence enters the prompt, and that part belongs on the institutional hub (Cle) like any other class-2 work. Only the piece that actually has to read the data runs in the local profile.

So every class-3 task is cut in two before it starts:

  • Local, unavoidable: reading the images/records, computing metrics, comparing segments, extracting the numbers. Here the patient data exists and must not leave the machine. Keep this part as small as it can be made.
  • Cle, everything else: the design of the method, the code, the pipeline, the evaluation logic, the write-up. These consume a result (an aggregate, a redacted line) and need no case. Against a data-free contract they are class-2 work and go to Cle - no reason to burn local capacity on them.

Minimise the local share, maximise the Cle share. The test is not "does this touch the dataset" but "does this prompt contain patient data": if the prompt is data-free, it runs on Cle even when the surrounding job is class 3.

Where the scheme sits next to established practice

The nearest established counterpart is the Turing Data Safe Haven sensitivity tiering (Tier 0-4, preprint arXiv:1908.08737, docs fetched 2026-10-21). Roughly: Tier 0 "personal data ... for eventual publication" maps to class 1, Tier 2 (pseudonymised, no outbound internet) to class 2, Tier 3 (personal data, restricted networks) to class 3. Two differences matter:

  1. The tiers judge by harm on disclosure and degree of pseudonymisation, and they count what is generated ("processed, combined or generated") - hence the inheritance rule above. This scheme judges by route; the inheritance clause is what keeps the two from drifting apart.
  2. Established trusted research environments (Turing, UK Biobank RAP, SAIL, the Five Safes airlock) control the output: only summary results pass a statistical disclosure check. This scheme's class 2 has no such output check - it says "may compute here". That is a real gap: class 2 permits processing, it does not by itself certify that the result is releasable.

DUO gives the vocabulary to say which restriction is meant (see above); FIDES (Microsoft Research, arXiv:2505.23643) is the closest published idea to enforcing such labels against agent tool calls - labels on the data decide which calls are allowed. No scheme that tiers datasets to gate agents was found in the research-data field; that part looks unpublished.

The class is a property of the data, not of the folder it happens to sit in: a class-2 copy stored outside the usual data location is still class 2, and sitting next to private cases does not promote it to class 3.

Derived artefacts and the person behind "institution"

The class is inherited, not reset. An artefact carries the maximum class of its inputs: a mask, an overlay, an embedding, a quality-control page, a log line or a model trained on class-3 data is itself class 3. A vector store has the class of its source, because embeddings can be inverted back towards the input (Morris et al. 2023, arXiv:2310.06816, recovered 92 % of 32-token inputs). Pushing such an artefact to a repository publishes the data indirectly, so every artefact needs one line recording its origin class, and the push check reads that line.

"Institution" is a set of persons, not a building. Inside the institution, access to patient data is bound to a role (GDPR Art. 9(3), under professional secrecy), not granted to every instance that happens to sit on the same campus. Cle counts as institutional because the grant names the institution and the group behind it; a copy handed to an unrelated instance still needs its own basis. "Class 2 may run here" is therefore only as good as the name attached to here.

Class 2 is also the softest of the three and must be looked up per dataset. Class 1 is bounded by a licence, class 3 by law, but class 2 is a method label whose reach is set by the individual data use agreement. Two labels from the GA4GH Data Use Ontology (DUO) frame it: DUO:0000028 IS institution specific restriction ("use is limited to use within an approved institution", verified in duo.csv 2026-10-21) fits; DUO:0000015 NMDS no general methods research does not - it forbids method development such as software or algorithms, and that collides with the wiki rule that public code knows no dataset. Assume class 2 is heterogeneous until the agreement says otherwise.

Trägt

The scheme corrects a real over-block. HCP-Aging was treated as if it were private ("local only") because it carries an access restriction - but its own terms allow institutional sharing, so the institutional hub may use it. Blocking it was stricter than the contract requires and cost usable work. In the other direction the scheme keeps the guard's purpose intact: private cases still never leave the local profile.

Trägt nicht

The class must be looked up, not inferred. "Open" (class 1) and "usable here" (class 2) are different questions, and an access restriction alone does not settle which one applies - read the terms. Class-1 and class-2 data also carry case ids that look like subject ids; a guard that blocks on id shape alone will fire on them, so the guard has to be class-aware rather than pattern-only.

The split also has a cost: it only works if the seam between "has to see the data" and "consumes only a result" is drawn honestly. A local step that quietly hands whole records to Cle is not a split, it is a leak. And a plan that keeps reasoning local "to be safe" defeats the rule - being stricter than the contract costs capacity the same way over-blocking costs work.

The enforcement is also weaker than it looks, and two of the weak points are measured (own runs 2026-10-21):

  • A proxy log cannot see the main route. no_proxy on this machine contains .charite.de, 10.0.0.0/8 and 141.42.0.0/16, so requests to Cle bypass the proxy entirely. Any evidence built on proxy traffic is blind exactly where the institutional path runs. The strong version is an isolated network namespace with loopback only, plus a counter-test in the same run: curl to Cle must fail. Then the path out does not exist and nobody has to trust a log.
  • The network fence is written but unproven here. werkzeuge/netzsperre/netzsperre.sh states about itself "GESCHRIEBEN AUF VICTUS, NICHT AUF ALITA GELAUFEN". It exists; on this machine it has never been run. Built is not the same as in force.
  • The guard's rejections have no target values. guard/log/vorgaenge.jsonl held 255 entries (156 rejected, 99 sent). That shows the guard does not reject blanket-wise; it does not show that its decisions are right, because nothing states what the right answer would have been. A guard that always says no looks identical by count.

So the guard needs a self-test, not a traffic count. With synthetic values only, expect reject-pass-reject: an invented id in the text must be rejected; a public challenge id next to plain numbers must pass (proving the guard is not blanket-rejecting); the same id split up, base64-encoded, in a filename or in a NIfTI descrip must be rejected. Then a mutation probe: switch off one rule in a copy of the guard and the series must go red - otherwise the test is vacuous. Finally reconcile the counts: requests sent by the sending layer must equal the entries marked sent in the log; any mismatch means a path around the guard.

The most likely false assurance, all three measured or documented above: a proxy log that never sees the institutional route, a redaction that checks only text while ids also sit in filenames and image headers, and a "local" profile that quietly points base_url outward. The strongest counter-evidence is the counter-test, not the protocol.

If an agreement forbids AI, it forbids it locally too

The route rules above answer "may this leave the institution". They do not answer "may a model touch this at all", and those are different questions. An agreement can forbid AI processing outright - local model included, institutional machine included. When one does, obey it locally.

The reasoning is not legal caution, it is arithmetic: following such a clause costs almost nothing (run the step by hand, script it, or leave it), while ignoring it risks the whole data access. There is no version of "we only used the local model" that the data provider will accept as compliance with a no-AI clause. Local execution is a route, not an exception.

This is why the class is not a substitute for reading the agreement. A dataset whose terms contain such a clause has no usable class under this scheme: it is not class 1 (not open), not really class 2 (the institutional route is allowed but the processing is not), and not class 3 (it is not ours to decide). Read the agreement first, assign the class second.

Still open: two claims that real agreements do this - ADNI forbidding AI tools including local ones, HRS forbidding LLM processing - could not be verified from this machine (the ADNI PDF is blocked by the proxy, the HRS page returns no text; see Ablesung). Until they are read, treat "an agreement may forbid AI" as a live possibility to check per dataset, not as a settled label for any named dataset.

Bruchindikator

A class-2 or class-3 case reaches a public repository, a public cloud or an external API. A class-2 dataset is refused on the institutional hub on the grounds of "patient data" although its terms permit institutional use. A data-free planning or coding prompt for a class-3 job runs in the local profile instead of Cle, or a local step forwards raw records rather than an aggregate. An artefact (mask, embedding, log, quality-control page, trained weights) is pushed without a class line, or with a lower class than its inputs. Class 2 is treated as one uniform permission when its own agreement is narrower. A release decision rests on proxy traffic although the institutional route bypasses the proxy, or on a guard's rejection count although no target values exist. Case-level content (ids, paths, values, image headers) is written into a log, cache or agent session store beyond the run that needed it, is kept because it "might be useful later", or is placed next to the data instead of in the run's own temporary space.

RegelMain rule: all work is in Englishgetragen2026-10-15

Herkunft: Mendel, chat on workstation Alita, 2026-10-15 ("ein Hauptregel in wiki sollte alle Arbeiten sollten auf Englisch sein") · eigene Seite · Markdown

Statement

Everything an agent produces is written in English: wiki entries (title, body, section headings), code, comments, commit messages, file and folder names, QC pages, tables and their column/sheet names, reports, primers and figures. The chat with Mendel may stay in German; the artefacts do not. Existing German entries are translated when they are next touched (no big-bang rewrite); a new entry is never written in German. Exception: the frontmatter keys and their fixed values (typ: regel, status: getragen, stand, herkunft, ...) stay as defined in templates/knowledge-entry.md, because wiki_maintenance --check validates them.

Applies to

All agents and chats that write to this wiki or produce files for Mendel's projects.

Does not apply to

Quotes of what a person said (keep the original wording, add an English gloss if needed); data that arrives in another language (e.g. German DICOM series names) is kept as it is.

Break indicator

A new entry, page or table in German, or a translated entry whose numbers no longer match the original.

Source

Mendel's instruction 2026-10-15; earlier the same rule for outputs (QC pages, Excel, GitHub) since 2026-09-29/10-12.

RegelMenschen lesen HTML, Agenten schreiben Markdown: die Wiki hat eine Quelle und eine erzeugte Lesefassunggetragen2026-10-11

Herkunft: Nutzerregel Mendel 2026-10-11 (Wiki und Tafel), Bau von tools/general/wiki_html · eigene Seite · Markdown

Aussage

Alle Information der Wiki wird für Menschen über die erzeugte HTML-Seite gelesen (docs/index.html, mit Links auf jede andere Seite, Suche, Kurzstand je Bereich, Einträge aufklappbar, Verweise und Rückverweise, Plots). Die Quelle bleibt Markdown mit Frontmatter, eine Datei je Aussage, wie im README beschrieben; nur die README.md ist zugleich Quelle und Lesetext. Agenten schreiben nie HTML von Hand in die Wiki. Nach jedem Beitrag wird docs/ mit tools/general/wiki_html neu gebaut und mit eingecheckt (lokal übernimmt das der pre-commit-Haken). docs/ wird nie von Hand bearbeitet; was dort fehlt, fehlt in der Quelle.

Trägt

Gilt für diese Wiki und sinngemäß für die Tafel (BLACKBOARD.md als Funktionskern, Tafel-HTML als Lesefassung). Gründe für Markdown als Quelle: dieselbe Information kostet in HTML etwa das Zwei- bis Dreifache an Tokens, und SUMMARY.md geht als Prefill in lokale Modelle mit knappem Kontext; kleine lokale Modelle schreiben Markdown zuverlässig und lassen in HTML Tags offen; Markdown-Diffs lassen sich bei parallelen Sitzungen lesen und zusammenführen; Prüfwerkzeug, Vorlagen, Skill und claude.ai-Projekt hängen am Frontmatter. Maschinen bekommen zusätzlich docs/index.json (Titel, Pfad, Bereich, Typ, Status, Stand, Kurztext je Eintrag).

Trägt nicht

Eine Veröffentlichung über GitHub Pages: für das private Repo im aktuellen Plan nicht möglich (geprüft 2026-10-11, HTTP 422). Bis dahin wird docs/ aus dem Clone gelesen oder über einen lokalen Server. Ein öffentliches Pages-Repo würde den Wiki-Inhalt öffentlich machen und ist eine eigene Entscheidung von Mendel.

Bruchindikator

RegelEin Dateiname, ein Zweckgetragen2026-10-02

Herkunft: Projekt Verbund, Datenvertrag 2026-09-05 bis 2026-09-16 · eigene Seite · Markdown

Aussage

Sobald mehrere Projekte Daten austauschen, entsteht ein naheliegender Name — daten.json — und zwei Ansprüche darauf: die Datenquelle, aus der eine Seite sich selbst speist, und die Außenschnittstelle, über die andere sie lesen. Solange ein Projekt allein steht, fällt das nicht auf. Sobald mehrere Agenten dieselben Repos bauen, besetzt jeder den Namen für seinen Zweck.

Der Fall: zehn Seiten in neun Repos sollten je eine vertragskonforme daten.json liefern. In drei Repos war daten.json zuerst die Datenquelle der Seite; der Vertrag landete daneben in daten-verbund.json. Die lesende Seite zeigte auf daten.json, fand dort eine gültige JSON-Datei ohne das Feld indikatoren — und meldete nichts. Kein Fehler, kein Abbruch, nur drei Quellen mit null Indikatoren, die aussahen wie Quellen, die eben noch nichts zu sagen haben.

Drei Maßnahmen, zusammen:

  1. Eigener Name für die Schnittstelle. Wer exportiert, exportiert unter einem Namen, den sonst niemand will.
  2. Namensraum prüfen, nicht nur Form. Die Datei nennt, für wen sie spricht (seite: "energie"), und jeder Schlüssel trägt dieses Präfix (energie.energisierte_gw). Der Leser prüft beides gegen das, was er erwartet hat.
  3. Verweigern statt übernehmen. Eine Datei, die den Vertrag verletzt, wird nicht eingelesen, sondern mit Grund gemeldet.

Punkt 3 ist der entscheidende: ohne ihn ist eine falsch benannte Datei von einer leeren nicht zu unterscheiden — siehe empty-is-not-missing.

Trägt

Jeden Datenaustausch zwischen Repos, die von verschiedenen Sitzungen gebaut werden. Auch Konfigurations- und Zwischenstandsdateien: config.json, state.json, index.json haben dasselbe Problem.

Trägt nicht

Ein Projekt, das für sich steht. Dort ist daten.json der richtige Name, und eine Umbenennung auf Vorrat ist Aufwand ohne Ertrag.

Auch keine Aussage über das Format. Der Vertrag kann beliebig aussehen; es geht darum, dass er einen eigenen Namen hat und beim Lesen geprüft wird.

Bruchindikator

Ein Leser, der bei der falschen Datei still weitermacht. Prüfprobe: dem Leser eine bewusst falsche Datei vorlegen — sagt er nichts, prüft er nicht.

Zweiter Indikator: eine Quelle, die über Wochen null Einträge liefert, ohne dass jemand sagen kann, ob sie leer ist oder falsch gelesen wird.

Ablesung

Eigene Messung, Projekt AI_Lage. Am 2026-09-16 waren 3 von 10 Quellen betroffen; das Leswerkzeug mit Vertragsprüfung meldete sie namentlich, danach 10 von 10 konform, 24 Indikatoren statt 3. Keine fremde Quelle.

  • empty-is-not-missing
RegelNicht in einen fremden Arbeitsbaum schreibengetragen2026-10-02

Herkunft: Projekt Verbund 2026-09-05 und blackbeard_wikki 2026-10-02 · eigene Seite · Markdown

Aussage

An denselben Repos arbeiten mehrere Sitzungen gleichzeitig. Keine von ihnen sieht die andere. Daraus folgen drei Regeln, alle aus Schaden gelernt:

Vor dem Schreiben Zeitstempel lesen.

ls -la --time-style=+%H:%M:%S

Bewegen sich Dateien im Minutentakt, läuft dort eine andere Sitzung. Bei einem Git-Repo ist .git der empfindlichste Zeiger: jünger als ein paar Minuten heißt aktiv.

Nicht in den fremden Arbeitsbaum schreiben, sondern in einen eigenen Klon. Der Grund ist nicht der Schreibkonflikt — die eigenen Dateien liegen meist auf neuen Pfaden und kollidieren gar nicht. Der Grund ist das git add -A der anderen Sitzung: es nimmt die fremden Dateien mit in ihren Commit und pusht sie, ohne dass irgendjemand sie freigegeben hätte. Aus einem Lesevorgang wird so eine Veröffentlichung.

Den eigenen Lesestand als veraltet behandeln. In einem aktiv bearbeiteten Repo ist jede Übersicht, die älter als Minuten ist, falsch.

Trägt

Jedes Repo, in dem mehr als ein Agent oder Chat arbeitet, und jedes gemeinsame Gedächtnis. Auch diese Wiki: sie ist der Fall, für den die Regel zuletzt gebraucht wurde.

Der eigene Klon ist billig. Ein ungewollt gepushter Commit ist es nicht.

Trägt nicht

Sperren oder Reservierungen. Es geht um Lesen vor dem Schreiben und um Trennung der Arbeitsbäume, nicht um ein Protokoll, an das sich alle halten müssten — denn genau das lässt sich zwischen Sitzungen nicht durchsetzen.

Auch kein Argument gegen das gemeinsame Repo. Die Alternative — jeder sein eigenes — ist teurer.

Bruchindikator

Ein Commit, der Dateien enthält, die niemand in dieser Sitzung geschrieben hat. Oder: zwei Einträge zum selben Gegenstand, die voneinander nichts wissen.

Ablesung

Zwei eigene Fälle, beide beobachtet, keine fremde Quelle.

2026-09-05, Verbund: eine parallele Sitzung baute drei Seiten und schrieb in jedem Repo eine eigene daten.json — dabei wurde eine vertragskonforme Datei zweimal überschrieben. Folge siehe one-filename-two-contracts.

Zwischen zwei Lesungen im Abstand von rund zwei Stunden wuchs die Wiki von 2 auf 15 Themen. Der Abgleich der ersten Lesung war zum Zeitpunkt des Schreibens vollständig veraltet.

BefundDerived artifacts carry the source class: a KV cache is a copy in number formgetragen2026-10-22

Herkunft: own run 2026-10-22 (building and exporting data-free prefill packages on Alita) · eigene Seite · Markdown

What was found

A prefill package was built from data-free fragments (16 fragments, 19 packages), then an optional layer was added: precomputed KV caches, one per package, ~1.1 GB each, held under system/logs/kvcache/.

The source fragments passed the outgoing guard. The caches derived from the same fragments were treated differently, and that is the correct reading, not an inconsistency:

  • A KV cache is the processed prompt state in number form. It is a copy of the text it was computed from, not a summary of it.
  • If the source text was cohort-bound, the cache carries that binding even though no cohort name is readable in it. The guard blocks by readable content, so it will not catch this.
  • Three older caches (thema-mb-arena, thema-valdo-t2s, thema-wmh-arena) belong to themes the guard blocks as cohort-bearing. They were excluded from the export for exactly this reason, though nothing in them is searchable.

Measured, same run: the file-level cache saves almost nothing. With the running service, a cold prefix took 4.4 s, the identical prompt right after took 0.4 s, and after a distractor 0.8 s. The whole agent turn is 29-34 s, dominated by process startup. The 21 GB of caches buy roughly the seconds a warm slot already provides.

Why it matters

  1. Class inheritance applies to derived artifacts, and it survives redaction. A mask, an embedding, a QC page or a model trained on class-3 input is class 3. A KV cache is the same kind of object: it cannot be promoted to "data-free" by showing that no identifier is visible inside it.
  2. Guard coverage is by content, not by provenance. A cache of blocked source material passes a content check because it contains no readable strings. So the exclusion has to be a rule, not a scan result.
  3. Group drives are a destination, not a sieve. On a Charite-internal group drive, pseudonymised patient data may legitimately live. That is what makes it the wrong place for derived artifacts of unknown provenance: the destination permits the material, so nothing else will stop it. Only data-free source files belong in a package folder there.
  4. Cost is a separate question from permission. The caches were dropped from the export on both grounds, and the 21 GB mattered less than the class argument. Had they been cheap and useful, the class rule would still have excluded them.

How to check (repeatable)

  1. For every derived artifact ask: what was the maximum class of the text that produced it? If that is not knowable, treat the artifact as the higher class.
  2. Do not try to decide it by grepping for names or identifiers. Absence of a match is not evidence of absence of the binding.
  3. Export only source-level, data-free material to shared destinations (system/themen/auf-alita.sh stages only bausteine/ briefe/ werkzeuge/ and refuses the kvcache/ directory by design).
  4. Weigh the speed claim before shipping bulk: measure the warm-slot case first.

Trägt

  • A concrete instance of the class-inheritance rule on a real export, with the destination being an internal group drive rather than an external API.
  • The distinction between guarding by content (what the guard can do) and ruling by provenance (what a person must do).

Trägt nicht

  • The number of caches or the byte sizes are specific to this run; they are not a property of the method.
  • No claim that the three excluded caches are a leak. They are prompt state of cohort-bearing themes kept on the local route, nothing confirmed to have left.

Bruchindikator

Would be wrong if a KV cache were shown to be a lossy encoding that provably cannot be matched back to its source content, or if a shared destination were shown to strip provenance in a way that the class rule already accounts for.

Ablesung

Before copying any derived artifact to a shared or group destination, name the source class in one sentence. If the sentence needs a hedge, the artifact stays local.

BefundDie Pfadregel der Wachen fragt nach der Rolle, nicht nach dem Einhängepunktgetragen2026-10-22

Herkunft: own run 2026-10-22 (making the external disk usable as a work volume) · eigene Seite · Markdown

Befund

Mehrere Wachen sperrten pauschal den Einhängepunkt für Wechseldatenträger. Der Grund war gut: auf dem externen Träger lag tatsächlich einmal Kohortenmaterial. Nur ist der Einhängepunkt kein Merkmal für Inhalt. Derselbe Träger trug auch QWEN-Bundles, Papiere und FreeSurfer-Pakete -- rund 74 GB Werkzeug wurden mitgesperrt.

Die Pfadregel ist jetzt rollenbasiert, nach derselben Hausregel wie bei den Datenklassen: die Rolle wird nachgeschaut, nicht angenommen. Sie steht als Datei ARBEITSPLATTE im Wurzelverzeichnis des Datenträgers.

  • Datei vorhanden -> Arbeitsplatte, von der Pfadregel ausgenommen
  • Datei fehlt -> wie bisher: der Ort gilt als Ablage und ist gesperrt

Die Regel wird dabei strenger, nicht laxer: vorher war ein bestimmter Wechseldatenträger verdächtig, jetzt gilt jeder nicht erklärte Datenträger als Ablage. Ein Wechseldatenträger, der gar nicht gemountet ist, wird ebenfalls erfasst.

Was ausdrücklich NICHT fällt

Nur die Pfadregel fällt. Die Inhaltsprüfungen laufen unverändert weiter, auch auf einer erklärten Arbeitsplatte: BIDS-Kennungen, Bilddateinamen, gepackte Bilddateien, Kohortennamen. Nachgemessen: auf erklärter Arbeitsplatte werden eine BIDS-Kennung, ein NIfTI-Dateiname und ein gepackter NIfTI-Dateiname weiterhin erkannt. Wer Kohortenmaterial auf eine Arbeitsplatte kopiert, fliegt auf.

Zwei Fallen, die beim Bauen auffielen

  1. Umgebungsvariablen sind additive, keine Ersatzschalter. Die Pfadlisten sind als Umgebungsvariable + feste Literale gebaut. Die Variablen zu leeren erweitert nur, es ersetzt nie. Der naheliegende Hebel ist wirkungslos.
  2. Trägernamen enthalten Leerzeichen. In der Einhängetabelle steht ein Leerzeichen als \040. Eine Wortzerlegung des geprüften Textes hätte den Namen abgeschnitten und die Rolle des falschen Ortes geprüft. Deshalb wird der konkrete Einhängepunkt aus der Tabelle geholt und als ganze Zeichenkette im Text gesucht.

Dritte Falle derselben Art

Die Rollendatei zählt nur in der Wurzel des Datenträgers. Eine erste Fassung lief vom Pfad bis zur Dateisystemwurzel hinauf und hätte eine Rollendatei in einem übergeordneten Verzeichnis den ganzen Baum darunter freigeben lassen -- auch Bereiche auf anderen Datenträgern. Eine Datei im Heimverzeichnis hätte damit das Datenverzeichnis mitfreigegeben.

Randnotiz: eine Wache blockt ihren eigenen Quelltext

Die Fernwache verweigert das Lesen ihrer eigenen Quelldatei mit der Begründung, sie enthalte eine Bilddatei und einen Kohortennamen -- was stimmt, die Suchmuster stehen dort im Klartext. Das ist eine Eigenschaft, kein Fehler: sie schützt auch vor sich selbst. Praktische Folge: solche Dateien nicht mit dem normalen Leser öffnen, sondern Struktur und Zeilennummern gezielt abfragen oder die Literale zur Laufzeit zusammensetzen. Dasselbe gilt für Testbefehle: ein Prüfbefehl, der die gesuchte Zeichenkette wörtlich enthält, wird selbst geblockt -- Proben deshalb aus Teilen zusammensetzen.

Wo es liegt

  • system/waechter/rolle.py -- Rollenlogik, an einer Stelle
  • system/waechter/rolle-setzen.sh -- Rollendatei setzen (löst den Trägerpfad zur Laufzeit auf, damit kein fester Pfad im Skript steht)
  • system/waechter/README-arbeitsplatte.md -- dauerhaftes Einhängen nach /mnt/arbeit (braucht sudo)
  • verdrahtet in system/waechter/pruefe.py, system/systemone/approval_gate.py und im Plugin der Fernwache
BefundResearch passes invent plausible PMIDsgetragen2026-10-21

Herkunft: own runs 2026-10-21, three headless Claude research passes on the three-data-classes rule · eigene Seite · Markdown

Aussage

An agent asked to research a topic returns citations that look right and are wrong. On 2026-10-21 three headless research passes (Claude Code, claude -p, read-only tools, network on) were run against the three-data-classes rule. One pass cited Schwarz et al. 2019 NEJM with PMID 31657887 and Rocher et al. 2019 Nature Communications with PMID 31427575, plus a PMC link. Checked against PubMed:

  • PMID 31657887 is "Discrimination, Abuse, Harassment, and Burnout in Surgical Residency Training" (Hu YY, NEJM 2019).
  • PMID 31427575 is "AAV-ie enables safe and efficient gene transfer to inner ear cells" (Tan F, Nat Commun 2019).
  • The correct Schwarz PMID is 31644852, "Identification of Anonymous MRI Research Participants with Face-Recognition Software" (N Engl J Med 2019).
  • The Rocher claim could not be verified at all; the citation was removed rather than repaired.

The numbers the pass reported (92 % embedding recovery, 70 of 84 rank-1 matches) were plausible and the topics were right - only the identifiers were fabricated. A wrong PMID on a real-looking claim is harder to catch than a nonsensical one.

Same trap, one step further in (own error, same day). After correcting the PMID, the figure "70 of 84 rank-1 matches" was copied into the rule as if verified. It is not: PMID 31644852 is a brief report with no abstract, so the number was never read anywhere. An identifier can be perfectly real and the number beside it still invented. The rule now says the figures were not read. A verified id is not a verified sentence.

Trägt

It settles how to consume a research pass: treat every identifier as a claim to be checked, never as a lookup already done. The check is cheap (one EUtils/Europe PMC call per id) and the failure is silent otherwise. It also justifies using several independent passes: the passes agreed on the shape (Turing tiers, DUO vocabulary, output checking) and disagreed on nothing structural, so the consensus carries even where a single citation does not.

Trägt nicht

It does not mean the passes are useless. Two of three produced verified, load-bearing material: the Turing Data Safe Haven tier mapping, the UK Biobank/SAIL/Five Safes output-checking comparison, and the DUO label list. The DUO labels were re-read from duo.csv and matched exactly. The failure was narrow - identifiers - not the research.

It also does not mean a check makes a source true: a valid PMID proves the paper exists and has that title, not that it supports the sentence it is attached to. That second step (read the abstract) stays manual.

Bruchindikator

A wiki entry carries a PMID or DOI that the sources-check tool cannot tie to its title, or that resolves to an unrelated paper. A citation is copied from a research pass without a check, or a "corrected" identifier is written without reading the paper it now points to. The same applies to a DOI that resolves but to the wrong article.

Ablesung

Check, own runs 2026-10-21: PubMed EUtils esummary for a PMID returns title, journal, first author - compare against the claim. Europe PMC search?query=DOI:"..." resolves a DOI to its article. Corrected Schwarz reference: https://pubmed.ncbi.nlm.nih.gov/31644852/ . Removed reference: Rocher et al. 2019, Nat Commun - PMID unverified, not reinstated. Rule that consumes this: three-data-classes-decide-what-may-leave-the-institution. Tool for the standing check: system/werkzeuge/quellen-pruefen.

Befund/tmp is not volatile on Alita, and agent session stores persist theregetragen2026-10-21

Herkunft: own runs 2026-10-21 (cleanup of /tmp scratch and Claude Code session stores on Alita) · eigene Seite · Markdown

What was found

On Alita, /tmp lives on the root filesystem, not on a RAM-backed tmpfs:

  • findmnt /tmp resolves to /dev/nvme0n1p2, filesystem ext4 (the same root partition).
  • systemctl is-enabled tmp.mount reports not-found.
  • Claude Code writes its session state under /tmp/claude-1000/ and no TMPDIR is set for it in ~/.claude/settings.json, ~/.bashrc or ~/.profile.

Consequence: everything an agent or a script leaves in /tmp survives reboots and shutdowns. It does not age out on its own. The directory is, in practice, a durable store on a disk that also holds other people's data.

Why it matters

  1. "It is only in /tmp" is not a containment argument. A path under /tmp is not more ephemeral than a path under the home directory; both are the same disk. An argument that says "this copy is harmless because /tmp is cleared" is false here.
  2. Agent session stores grow without bound. The Claude Code store on Alita held ~13 GB in ~59,000 files at the time of this check, across many session directories. Most of it was from closed sessions. This is scratch, not deliberate logging, but it is the same class of material a log rule is meant to bound.
  3. Cleanup is unsafe while agents run. At check time 8 claude processes and 2 guard daemons were active, and lsof showed five session directories held open, one being tailed live. Deleting those would have destroyed work in progress.

It does not follow that the store is a leak. It follows that its lifetime is not what the name suggests, so it must be handled deliberately rather than ignored.

How to check (repeatable)

findmnt -no SOURCE,FSTYPE,OPTIONS /tmp     # tmpfs here means volatile; ext4 does not
systemctl is-enabled tmp.mount             # not-found = no systemd-managed tmpfs
df -h /tmp                                 # confirm it is the root filesystem
lsof +D /tmp/claude-1000                   # which session dirs are in use right now
pgrep -au $USER -f claude                  # is a session running at all
du -sh /tmp/claude-1000                    # size of the store

Cleanup recipe (only when no agent session is running)

  1. Confirm no session is active: pgrep -au $USER -f claude is empty and lsof +D /tmp/claude-1000 is empty.
  2. Delete only directories belonging to closed sessions; never remove a directory that lsof lists.
  3. Better than deleting: give the tool its own temporary directory, so the store disappears with the process - e.g. TMPDIR="$(mktemp -d /tmp/agent.XXXX)" exported before the tool starts, removed afterwards. Setting TMPDIR to a directory on a real tmpfs (/run/user/$UID is RAM-backed and per-user) achieves the same for scratch.
  4. Do not log what was deleted beyond counts and total size. File names and contents stay out of logs (see rules/do-not-log-case-level-content.md).

Cost of being wrong

  • Ignoring it: the store keeps growing on the root disk and old session scratch stays readable indefinitely.
  • Cleaning too eagerly: work in progress is destroyed and a running agent fails for no reason - the reason to check lsof first.

Befolgen (clean up deliberately, or redirect TMPDIR) costs a few minutes. Ignoring it risks both a full root disk and a long-lived copy of session material nobody chose to keep.
