Aussage

  1. "ALITA" is not a working folder on the workstation. It is the Charité group drive, reachable over the wiki hub (ssh temuuleu@s-csb-wiki-hub.charite.de, path CSB_NeuroRad/temuuleu/ALITA, mounted there as //s-vfs-mgd03.charite.de/ag-csb_neurorad$). The workstation itself is called Alita (Alita-MS-7D91) -- on it, "move to Alita" is a no-op. Search the wiki and the skills before searching the disk.
  2. A profile that runs on a remote model may not mount or read the external-disk mount point under /media: the data guard refused that location outright, because cohort data lives there. Work on the group drive therefore goes by scp/rsync -- from the local profile or by hand, not from the remote one.
  3. Check the space on the target first. The group drive is a shared 12 TB volume that was 84 % full (2.0 TB free) on 2026-10-17, while ALITA itself holds 126 GB (DATA 79 GB, ARCHIVE 28 GB, QUALITY_CONTROLL 18 GB). It is not a parking space for 70 GB of model weights.
  4. "Move" on the group drive means copy, verify by checksum, then report -- never report done from the rsync exit code. Scripts do not delete there; the user edits files (xlsx) in place, so fetch, extend, copy back with --update. Source: the alita-storage skill.
  5. A password typed into the chat is burned. Interpolating it into a shell command is refused by the permission classifier as a brute-force/credential pattern (sudo: a password is required even with -S, plus a block on the first attempt), and the secret stays in the transcript and the logs. Say so and ask the user to change it; hand over the finished sudo lines instead of running them.

Trägt

Own run 2026-10-17 on the workstation: find ~ -maxdepth 4 -iname 'alita*' returned only name-adjacent hits (~/.MATLABConnector/Alita-MS-7D91, modelle/...), while ALITA in capitals existed solely in the Claude Code skill ~/.claude/skills/alita-storage/SKILL.md (2026-08-28) -- one grep of the skill folder answered what the disk search could not. Key login to the hub works without a password (ssh -o BatchMode=yes ... 'echo KEYLOGIN-OK'), so a transfer needs no credentials in the command. df on the group drive: 12 TB, 11 TB used, 2.0 TB free (84 %).

Trägt nicht

The entry does not make a transfer safe by itself: the best move target for publications is a public archive (GitHub/Zenodo), and the group drive holds pseudonymised patient data, so what goes there must already be cleared for it. Rule 4 covers the checksum discipline, not the decision which files belong on the group drive at all.

Jeden Fehler in der Kette benennen (meist sind es zwei bis drei: eine falsche Annahme, ein fehlender Check, ein Exit, wo Warten richtig waere). 3. Abhilfe im Code, nicht im Gedaechtnis: der Check wandert an die Stelle, die die Entscheidung trifft (modellstart, grossauftrag, agent.sh), mit Sicherung *.vor-<datum>-<grund> und einem Test der Entscheidung ohne Start. 4. Befund ins Wiki (local_llm_operation/findings) mit Bruchindikator, Verweis in SUMMARY, eine Tafelzeile. 5. Agent bleibt am Leben: Fehler beim Modellstart fuehren zu Warten und erneutem Versuch, nie zum Schliessen des Fensters. Nur der Nutzer schliesst Clara.

Aussage

Teilen sich Sprachmodell und GPU-Trainings eine Karte, darf der Start des Modellservers nie blind systemctl start sein. Vorher drei Dinge pruefen:

  1. Wer haelt die Karte? Eine Sperrdatei mit lebender PID (hier ~/data/work/.gpu-belegt, geschrieben von der Rechen-Warteschlange). Lebt sie, kommen nur Profile in Frage, die als "neben einem Training ladbar" markiert sind (Registry-Feld sperre_beachten: false; auf Alita das 177B-MoE mit Experten im RAM, 7,5 GiB VRAM).
  2. Wie viel ist frei -- und wie viel davon ist schon versprochen? nvidia-smi memory.free luegt in den ersten Minuten eines Laufs: das Training hatte beim Einbau nach 29 s noch 0 MiB auf der Karte, 20 GiB angemeldet. Deshalb den angemeldeten Bedarf des laufenden Eintrags (--vram des Halters oder der erste offene Eintrag der Schlange) minus das, was der Halter samt Kindprozessen laut nvidia-smi --query-compute-apps schon belegt, vom freien VRAM abziehen.
  3. Passt ein Profil? Freier Rest >= braucht_mib des Profils -- dieselbe Schwelle, auf die das Startskript selbst wartet. Reihenfolge: eingestelltes Profil zuerst, dann die uebrigen, groesstes zuerst.

Passt nichts: nichts starten, rc 3, Meldung mit Halter und Zahlen. Nicht einen wartenden Dienst zuruecklassen -- der nimmt sich die Karte in der Luecke zwischen zwei Laeufen, und der naechste Lauf findet sie voll.

Das gewaehlte Profil gilt nur fuer diesen Start (systemctl --user set-environment QUANT=..., gleich wieder geloescht). Der eingestellte Standard bleibt, damit die Schlange am Ende und die Wache nach einem Absturz den Server im gewohnten Profil zurueckholen. Der Agent liest sein Kontextfenster vom LAUFENDEN Modell (/v1/models), nicht aus der Einstellung.

Traegt

Jeden Agentenstart (clara, agent) auf einer Maschine, auf der eine Warteschlange Trainings auf dieselbe Karte legt. Beim Einbau lief ein 20-GiB-Lauf: Entscheidung ohne Reservierung "flash passt (23 314 MiB frei)", mit Reservierung "nur 2 834 MiB frei, braucht 7 500" -- rc 3, Schlange lief ungestoert weiter.

Traegt nicht

Trainings ohne Sperrdatei und ohne angemeldeten Bedarf: dann zaehlt nur der momentan freie VRAM, und die Luecke zwischen zwei Laeufen bleibt eine Falle. Auch nicht die Gegenrichtung: laeuft der Agent auf dem kleinen Profil, muss die Schlange fuer einen schweren Lauf den Server weiterhin anhalten und wartet dafuer, bis kein Agentenaufruf mehr laeuft (Staffelstab).

Startlog mit "Warte mit dem Laden" waehrend ein Lauf rechnet; ein Lauf, der mit CUDA-OOM stirbt, waehrend das Sprachmodell antwortet; RAM-Warnung beim MoE-Profil (40 GiB gewuenscht, 24 verfuegbar neben einem Training): dann kommen die Experten von der Platte.

MechanismusEin MoE-Modell laeuft auf einer GPU, auf die es nicht passtgetragen2026-08-29`-ngl` plus `-ncmoe`: ein 35-B-Modell auf 8 GB VRAM, 19,4 t/s

Herkunft: Projekt local_models, Victus, 2026-08-29 · eigene Seite · Markdown

Aussage

Ein dichtes Modell muss fuer jedes Token alle Gewichte lesen, ein Mixture-of-Experts nur die aktiven. Damit laesst sich ein 35-B-Modell mit 3 B aktiven Parametern auf einer 8-GB-Karte interaktiv betreiben: -ngl 99 legt Attention, Embeddings und KV-Cache ins VRAM, -ncmoe N laesst die Expert-Gewichte der ersten N Layer im RAM und rechnet sie auf der CPU. Beides arbeitet gleichzeitig.

Gemessen auf Victus (RTX 4070 Laptop, 8 GB; Qwen3.6-35B-A3B UD-IQ4_XS, 40 Layer):

-ncmoe 99 (alles CPU) -ncmoe 34 (6 Layer GPU)
VRAM 5132 MiB 6733 MiB
Decode 15,9 t/s 19,4 t/s
Prefill, warm 160 t/s 180-306 t/s

Traegt

Dass sich die Modellgroesse von der Kartengroesse entkoppeln laesst, solange das Modell MoE ist. Die Richtung der Abwaegung: jeder Expert-Layer, der auf die GPU wandert, bringt ein paar Prozent.

Traegt nicht

Ein dichtes Modell. Dort gilt nichts davon - ein dichtes 27 B blieb auf derselben Karte bei etwa 4 t/s. Auch kein Argument fuer grossen Kontext: der Prefill laeuft CPU-seitig und ist compute-bound, ein 16k-Prompt kostet rund eine Minute.

Bruchindikator

Decode-Rate faellt unter die Rate bei -ncmoe 99. Dann ist nicht die Aufteilung schuld, sondern RAM-Mangel - Modellseiten werden verdraengt und von SSD neu gelesen. Erster gemessener Prefill auf Victus: 6 t/s statt 243.

Ablesung

Eigene Messung, Tier 1b-aequivalent: llama.cpp b10603, CUDA 13.3, /v1/chat/completions mit timings. Nicht uebertragbar auf andere Karten ohne Nachmessen.

MechanismusEin Slot, und die Historie nie umschreibengetragen2026-08-29`-np 1`, und warum Prompt-Kompaktierung den Cache zerstoert

Herkunft: Projekt local_models, Victus, 2026-08-29 · eigene Seite · Markdown

Aussage

llama-server legt standardmaessig mehrere Slots an, jeder mit eigenem Prefix-Cache. Ein sequenzieller Client landet dann abwechselnd in verschiedenen Slots, und der System-Prompt wird jedes Mal neu prefillt. -np 1 haelt alles in einem Cache.

Daraus folgt eine zweite, wichtigere Regel: bei append-only Verlauf traegt der Prefix-Cache den gesamten Kontext, pro Schritt werden nur die neuen Tokens prefillt. Jede Operation, die die Historie umschreibt - Kompaktierung, Zeitstempel im System-Prompt, nachtraegliches Kuerzen - wirft den Cache weg und erzwingt vollen Re-Prefill.

Beleg aus dem Serverlog: nach einem Treffer meldet der Server selected slot by LCP similarity, f_sim_best = 1.000 und wertet nur noch 4 Token statt 80 aus.

Traegt

Die Entscheidung -np 1 fuer jeden sequenziellen Client. Und die Entscheidung gegen Prompt-Kompaktierung in Agent-Schleifen auf lokaler Hardware.

Traegt nicht

Batch-Durchsatz. Dort ist das Gegenteil richtig: mehrere parallele Anfragen lasten die Expert-Matmuls besser aus. Zwei Startprofile anlegen, eines je Zweck.

Bruchindikator

Jeder Aufruf kostet gleich viel Prefill, obwohl der Prompt sich nur am Ende verlaengert. Dann greift der Cache nicht.

Ablesung

Eigene Messung, llama.cpp b10603, Serverlog mit -lv 3.

Aussage

  • For an agentic workflow, the literature does not support "medical" models as a default: a purpose-built medical agent that ran fully on-premise reached competitive diagnostic reliability on MIMIC-IV benchmarks, i.e. the decisive factors were local control plus a reliability/uncertainty layer, not a "medical" pre-training flavour (unverified) [1].
  • General vision-language models are close to — and sometimes above — specialist medical models on concrete findings, while medical VLM families such as MedGemma are built for data-efficient fine-tuning and exceed similarly sized general generative models on medical image QA and agentic evaluations [5][6][7].
  • Quantisation is a real, measurable trade-off, not free: on a clinical extraction task (mRS score from notes) larger models and higher precision reduced error, but performance plateaued at 4–5 bits — exactly the regime that fits a ~27B model into one 24 GB GPU [12].
  • Ternary / 1.58-bit is no longer only "train from scratch": post-training ternary quantisation was scaled to 70B parameters with only a modest accuracy drop versus a from-scratch 1.58-bit baseline (unverified), which makes ultra-low-bit weights a serious option when VRAM, not VRAM-speed, is the binding constraint [14].
  • "It fits in 24 GB" is achievable even at very low bit-widths: 2-bit quantised 65B models can be fine-tuned on a single 24 GB GPU with modular low-rank adaptation [15].
  • Tool/function calling is where a local model can quietly fail, and current evaluation practice is the weak spot: benchmark, agent and tool-use harnesses are heterogeneous and not yet a settled standard [4], while agentic clinical benchmarking shows that agent systems (not just the base model) must be evaluated end-to-end [2][3].
  • Small and mid-size language models can be preferable for agentic healthcare tasks because of deployability, cost and operational efficiency, provided the task is well scoped [16].
  • Local, open-weight deployment is already demonstrated for exactly our data class: privacy-preserving local LLMs for structured retrieval from clinical text [17], local LLMs accelerating review of historic echocardiogram reports [18], locally deployed LLMs for BI-RADS-compliant mammography reporting under privacy constraints [19], and open-weight LLMs extracting structured information from brain MRI reports [8].
  • German is not a solved problem for small local models; open models were benchmarked for German clinical documentation [20] and for extracting attributes from German pathology reports [21], and German appears repeatedly as a separate evaluation axis rather than a free by-product of English capability.
  • A 71 GB MoE quantised to ~IQ3 stays larger than 24 GB of VRAM; running it means offloading to the 62 GB of RAM, which changes the latency profile. That specific configuration is unverified (no retrieved source measured it).

Practical recommendation (as written for our setup)

Constraint recap: one RTX A5000 with 24 GB VRAM, 62 GB RAM; agentic use on pseudonymised imaging data; needs German + English, Python/log work, tool calling, optional MRI screenshots.

  1. Default to a general mid-size dense model, ~27B, at 4-bit, as the workhorse — not a "medical" model. Evidence: quantisation quality plateaus at 4–5 bits [12], 4-bit is the safe operating point, and the on-premise agent result shows reliability/governance — not medical pre-training — is what enabled clinical translation [1]. German capability must be validated on our own texts rather than assumed [20][21].
  2. Reserve a medical VLM (MedGemma-class) for the imaging/screenshot path, where its medical encoder and data-efficient fine-tuning are the differentiator, and where general models are only close rather than better [5][6].
  3. Do not push the vision path below 4-bit. Ultra-low-bit quantisation degrades visual capability specifically [13].
  4. Treat tool calling as the primary acceptance test, evaluated end-to-end at the agent level, because the harness is part of the system and the evaluation standards are still unsettled [2][3][4].
  5. Keep KV cache at Q4 (or Q4K/Q3V) and leave Q2 key precision alone, since low-bit KV policies can preserve perplexity while destroying task behaviour, and Q2 keys were catastrophic [22].
  6. If VRAM is the binding constraint, ultra-low-bit is viable but must be re-validated: ternary weights are now reachable post-training at scale [14] and 2-bit models can even be fine-tuned on one 24 GB GPU [15], but expect measurable degradation versus 4-bit [13].
  7. Run the 71 GB MoE only with explicit RAM offloading and measure latency — it does not fit in VRAM, and no retrieved source measured this configuration for our workload (unverified).
  8. Document the risk framework and governance alongside the deployment: local deployment answers the data-protection question (demonstrated repeatedly [17][18][19][8][9][24][25]) but does not by itself answer safety, uncertainty or regulatory alignment [1][16][23].

Aussage

"System One" models (TypeSafe's Jev and its open clones) answer typed questions (Choice, Score, yes/no) with a probability in 30-500 ms instead of generating text. Inside an agent harness they fit four decision points: (1) which model handles the turn, (2) which prepared context (profile, skill set, saved prefix slot) it starts from, (3) whether a tool call runs without asking, (4) whether a result passes (task done, source supports the claim). Not to be confused with JEPA (LeCun's joint-embedding world models: V-JEPA 2.1, VL-JEPA, LeWorldModel): no JEPA model was found that makes harness decisions.

State 2026-10-19 (foreign numbers unless marked):

model open evidence use here
Jev (TypeSafe) no, hosted API only JevBench reference 71.5; vendor's own workflow evals 67.8 % vs 74.1 % of a frontier model only for text without data
H2O-Lightning-4B (h2oai, Qwen3.5-4B) Apache-2.0, GGUF model card: JevBench v1.1 composite 72.5 (> Jev 71.5), ECE 0.017, 29 ms p50 strongest local candidate

Traegt

  • Fixed rules before the model: anything that touches patient data goes to the local model, never decided by the classifier; a deterministic deny list (cohort guard) runs before any learned approval gate; unclear cases escalate to the human. A reviewed gate is safer than blanket allowlist entries for whole command classes.
  • A hosted System One model sees the state it judges: data-free text only. Local clones speak the same wire format (POST /v1/systemone), so plugins switch by base URL.
  • Order: local service (decider-4b, H2O-Lightning-4B) -> own test set (routing cases, real approval requests from the harness logs, acceptance checks) scored as coverage at 5 % error against embedding kNN -> one week shadow mode (decide and log, do not act) -> live with threshold p >= 0.8, below that unchanged.

Aussage

Ein Entscheidungsmodell (Jev von TypeSafe, offen: Laya von Convai) liefert in 30 bis 100 ms eine Wahl mit Wahrscheinlichkeit statt Text. Als Orchestrator taugt es nur dort, wo beide Ziele gleichzeitig antworten koennen. Auf einer 24-GB-Karte sind die grossen Profile (27B dicht, 177B-MoE) exklusiv: ein Wechsel kostet 20 bis 40 s Laden plus Verdraengung des Vorgaengers. Eine Weiche je Anfrage zwischen diesen Profilen ist darum ein Fehlentwurf; die Weiche gehoert zwischen das grosse residente Modell, ein kleines residentes Nebenmodell und das Cloud-Modell.

Stand der Recherche (alles Fremdzahlen, siehe Ablesung):

Modell Groesse, Lizenz Latenz Treffer (fremd gemessen)

Jev (TypeSafe, API) geschlossen, $0,042/M Token 70-500 ms, Median 0,65 s typed decisions 0,73; Banking77 0,87; Routing-Bench 67,8 % gegen 74,1 % der Konkurrenz; 40/40 in einem Vier-Stufen-Test

Qwen2.5-3B als Klassifikator (arXiv 2604.02367) 3B 988 ms Median 0,78-0,79; Luecke 6-8 Punkte zur Produktionsschwelle 0,85

LLMRouterBench (400k Faelle, 33 Modelle) und RouterArena (ICLR 2026) finden, dass viele Router, auch kommerzielle, eine einfache kNN-Baseline nicht zuverlaessig schlagen. Laya ist rund 8-mal schneller als Jev und besser kalibriert (ECE 0,08 gegen 0,25), aber ohne Feinjustierung fast Zufall auf typisierten Entscheidungen; die 24/30 auf Victus kamen mit nur drei Zielen.

Traegt

  • Weiche VOR dem Agenten (nicht als Tool im Agenten, siehe Victus-Befund) mit hoechstens drei Zielen, die ALLE sofort antworten koennen: klein (residentes Nebenmodell <= 9B), gross (laufendes Hauptprofil), schwer (Cloud). Schwelle p >= 0,8, darunter an gross.
  • Das Profil flash (Flash-Next IQ2_XS, 6 GB VRAM) laesst neben sich ein kleines dichtes Modell auf der Karte zu; erst damit gibt es zwei lokale Ziele fuer eine Weiche. Mit dem 27B (21 GB) bleibt nur klein-CPU oder Cloud.
  • Laya als Dienst (laya-serve, CPU, ~1,6 GB RAM): 0,1 s je Entscheidung. Ohne Dienst 6-7 s Modellladen je Aufruf.
  • Vor jeder Einfuehrung: 60 Faelle mit Soll-Label (local_models tools/laya/faelle/route.jsonl) gegen Embedding+kNN auf demselben Embedding-Server (Port 8001) messen. Gewinnt kNN, braucht es kein Laya.

Traegt nicht

  • Profilwechsel je Anfrage (q4 gegen flash gegen flash-s): Ladezeit und Exklusivitaet der Karte machen die Weiche hier sinnlos.
  • Zero-shot-Einsatz von Laya fuer feine Kategorien (Banking77 0,43). Mehr als drei bis vier Ziele.
  • Die Konfidenz als Garantie (Victus: zwei Fehler bei 0,96/0,97).
  • Dass Laya 0.4.0 auf Alita ohne weiteres laeuft: es verlangt PyTorch 2.14 und transformers 5.x, die Umgebung dl hat 2.6. Eigene CPU-Umgebung noetig (Wheel plus 2,5 GB Gewichte ueber die Telefonleitung).

Bruchindikator

Auf den 60 Routing-Faellen liegt Laya nicht mindestens 5 Punkte vor Embedding+kNN, oder schwere Anfragen landen bei p >= 0,8 regelmaessig beim kleinen Modell.

Jev gibt es nur als gehosteten Dienst (api.typesafe.ai, POST /v1/systemone, SDK pip install typesafe-sdk, auch ueber OpenRouter: 0,042 $/M Eingabetoken, 32k Kontext). Aussage

Drei Fine-Tunes von Qwen3.8-27B sollen bei fast gleicher Genauigkeit weniger Denk-Token erzeugen. Die Zahlen stammen von den Herstellern, berichtet im Video:

Modell Versprechen Lizenz
ThinkingCap (BottleCapAI) 37 % weniger Token ueber 12 Benchmarks, Genauigkeit 86,6 auf 85,8 klein-gewerblich und privat
Swift 1.5 (UkisAI) bis 58,5 % weniger; LiveCodeBench 77 auf 81,7 % bei 11 200 auf 8 400 Token eigene, frei bis 1 Mio. $ Umsatz
QwenPi fuer den Pi-Harness; medium so gut wie Basis-xhigh auf Terminal Bench, 41 % weniger Output Apache 2

Fuer Victus zaehlt etwas anderes: Qwen3.8-27B ist dicht. Pro Token wirken alle 27 Mrd. Parameter, beim jetzigen Qwen3.6-35B-A3B etwa 3 Mrd. Expert-Offloading greift bei einem dichten Modell nicht.

Eigene Schaetzung, nicht gemessen: Q4 rund 16 GB, davon passen etwa 6,5 GB ins VRAM. Die restlichen rund 10 GB muessen je Token aus dem RAM gelesen werden. Bei rund 60 GB/s ergibt das 5-8 t/s Decode, gegen gemessene 30-35 t/s beim MoE. Auch 58 % weniger Denk-Token holen einen Faktor 4-6 nicht ein.

Dazu kommt der Speicher: 16 GB neben den 22 GB des MoE-Modells passen nicht in 30 GB RAM. Ein Wechsel heisst jedes Mal neu laden.

Traegt

Nichts. Die Tabelle ist Herstellerangabe aus zweiter Hand, die Geschwindigkeit ist eine Rechnung.

Traegt nicht

Die Annahme "weniger Denken = schneller" laesst sich nicht von einer RTX Pro 6000 mit 96 GB (Testmaschine im Video) auf 8 GB uebertragen. Dort ist das Modell decode-gebunden im VRAM, hier im RAM.

Bruchindikator

Ein gemessener Decode ueber 15 t/s fuer ein dichtes 27B auf Victus. Dann ist die Rechnung oben falsch und der Vergleich offen.
