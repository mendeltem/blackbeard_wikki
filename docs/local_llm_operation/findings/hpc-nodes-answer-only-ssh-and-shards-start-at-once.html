Cluster nodes answer only on SSH from the intranet; a GPU share starts at once, a whole GPU waits

TypBefundStatusgetragenStand2026-10-16Herkunfttests from the institute intranet against the institute SLURM cluster, 2026-10-16Zuletzt geändert2026-10-16 agent_tooling, cmb_detection, local_llm_operation: environment isolation on shared clusters, data-agnostic public code, label map on thick slices, cluster ports and GPU shards (2026-10-16, with sources)Verwiesen vonvLLM from PyPI fails on a CUDA 12.7 cluster driver; the cu129 release wheel plus a CPU torchcodec works (local_llm_operation)Quelleknowledge/local_llm_operation/findings/hpc-nodes-answer-only-ssh-and-shards-start-at-once.md

Aussage

  1. From two intranet hosts, the cluster's compute and login nodes accepted only port 22; 8000, 54321 and 443 on the nodes were refused ("No route to host"). A service on a node (an LLM API) is therefore reachable from the intranet only through an SSH tunnel or a gateway inside the intranet.
  2. GPU partition inventory (sinfo -o "%N %G"): 20 x A100 40 GB, 7 x A100 80 GB, one node with 2 x L40S 48 GB; each GPU offers 4 GRES shards. A job asking --gres=gpu:1 was scheduled about 9 h ahead; the same job with --gres=shard:1 started within seconds. A training needing ~1.8 GiB fits a share. A model needing a whole 80 GB card competes for 7.

Trägt

Port probes with bash /dev/tcp from two hosts; squeue --start and job start times of 2026-10-16.

Trägt nicht

Queue times change by the hour; the port policy can change with the cluster configuration.

Bruchindikator

A port probe that connects; squeue --start that shows short waits for whole GPUs.

Ablesung

Own measurements 2026-10-16. SLURM GRES sharding: https://slurm.schedmd.com/gres.html#Sharding (Slurm documentation).
